1. Архитектурное ядро: Модель-Представление-Контроллер (MVC)
Проект четко разделен на слои. Взаимодействие между ними происходит через события (Impulsys) и прямые вызовы API.

Слой Модели (Core)
Здесь сосредоточена бизнес-логика и структура данных. Этот слой ничего не знает о визуализации (спрайтах, рендеринге).

Atom: Базовая единица логики. Содержит контакты (Contact) и функцию обработки (processFunc).
Assembly: Универсальный контейнер. Умная архитектура: это и "схема" (контейнер для других атомов), и "нод" (может иметь входы/выходы).
Ключевая механика: Использует ConductorPort для проброса сигналов снаружи внутрь. ConductorPort создает пару контактов (External/Internal), которые связаны друг с другом напрямую, создавая эффект "проходного" контакта.
Blueprint: Сериализуемое описание структуры. Assembly создается на основе Blueprint. Это позволяет сохранять и загружать схемы.
Contact: Точка передачи данных. Реализует отложенное распространение сигнала через SignalQueue, что предотвращает переполнение стека (Stack Overflow) в циклических схемах.
Слой Представления (Editor & UI)
Отвечает только за отрисовку и ввод пользователя.

NodeEditor: Центральный контроллер UI. Управляет канвой, зумом, выделением и связями. Не хранит логику атомов, только их визуальные представления (NodeView).
NodeView: Визуальный представитель Atom. Подписывается на изменения в Contact и обновляет цвет/текст, но не меняет данные модели напрямую (кроме инпутов).
ecs (Entity Component System): Надстройка для оптимизации рендеринга.
Вместо того чтобы обновлять sprite.x/y каждого узла каждый кадр (что медленно), данные о позиции записываются в PositionComponent.
RenderSystem один раз за кадр проходит по всем сущностям и обновляет их координаты. Это разгружает процессор при большом количестве нод.
Слой Контроллера (System)
Связует Модель и Представление.

Main: Точка входа. Управляет "стеком" редакторов (когда вы входите внутрь Assembly, создается новый NodeEditor). Хранит ссылку на текущий активный контекст.
system.commands: Реализация паттерна "Команда". Каждое действие пользователя (создать ноду, соединить провода) оборачивается в объект Command. Это позволяет легко реализовать Undo/Redo через UndoManager.
Impulsys: Глобальная шина событий. Позволяет NodeEditor и Main общаться без жестких ссылок. Например, нода отправляет событие NODE_CLICKED, а NodeEditor решает, выделить её или начать перетаскивание.
2. Ключевые взаимосвязи и Потоки данных
А. Создание Атома (Instantiate Flow)
Пользователь кликает в меню "Add NAND".
Main -> NodeEditor.createAtom.
NodeEditor создает CreateAtomCommand.
Команда берет Blueprint из AtomRegistry (библиотека определений).
AssemblyFactory.createAtom создает экземпляр Atom (или Assembly, если внутри есть другие атомы).
Атом добавляется в Assembly.internalAtoms.
Команда отправляет импульс ATOM_RESTORED.
NodeEditor ловит импульс и создает NodeView для этого атома, регистрируя его в ECS.
Б. Распространение Сигнала (Simulation Flow)
Пользователь меняет значение на NumberInput в UI.
Записывается в Contact.value.
Contact ставит задачу в SignalQueue.
На следующем тике SignalQueue выполняет _propagate.
Значение передается связанным контактам (Linked Targets).
Если контакт принадлежит Atom, вызывается Atom.onContactChanged.
Атом ставит задачу на пересчет _calculate.
Атом выполняет логику (например, !(A && B) для NAND) и пишет результат в выходной контакт.
Цикл повторяется для следующего атома.
В. Вход в Подсборку (Drill-Down)
Двойной клик по NodeView.
NodeView отправляет OPEN_ASSEMBLY_REQUEST.
Main проверяет, является ли атом Assembly.
Main создает новый NodeEditor для этой сборки и помещает его в стек поверх старого.
Старый редактор блокируется (blocker sprite), чтобы клики не проходили сквозь.
3. Особенности и "Фишки" кода
ConductorPort как паттерн "Шлюз":
В коде реализован изящный способ проброса контактов. У Assembly есть порты (Input/Output). Снаружи это обычные контакты, но внутри они связаны с "зеркальными" контактами. Это позволяет внутренней схеме соединяться с "внешним миром" через простые связи, не делая исключений в логике симуляции.
Гибридный ECS:
Использование ECS (ecs.core.World) только для рендеринга — интересное решение. Обычно ECS используется для всей логики игры/симуляции. Здесь же оно служит слоем кэширования: NodeView пишет в компонент, а RenderSystem применяет изменения к спрайту. Это позволяет легко включать/выключать оптимизацию (_useEcsRender).
Native Windows Integration:
Код содержит C++ вставки (@:cppFileCode) для работы с Windows API (WindowController). Это позволяет делать окно полупрозрачным (DWM Blur, Layered Window) и кликабельным ("пробивным" для мыши), что необычно для веб-ориентированного Haxe/OpenFL и указывает на использование проекта как Desktop-инструмента.
Разделение Logic и Composite:
В AssemblyFactory есть проверка:
Если у Blueprint есть logic -> создается Native Atom (логика на Haxe).
Если нет logic, но есть internalAtoms -> создается Composite Assembly (схема из других атомов).
Это позволяет расширять систему пользовательскими нодами без перекомпиляции.
