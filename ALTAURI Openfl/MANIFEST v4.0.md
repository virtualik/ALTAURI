# ALTAURI MASTER MANIFEST v4.0

**The Flow Programming Architecture**

---

## 1. Статус проекта: Stable Production Core

**Текущая версия:** v3.6 (Code Name: "Flat Stack")

**Ключевое достижение:** Полная ликвидация рекурсии в ядре вычислений и оптимизация работы с памятью (GC). Система готова к созданию графов любой сложности без риска переполнения стека (Stack Overflow) и с минимальным влиянием на сборщик мусора.

---

## 2. Архитектурная Модель (Layered Cake)

Проект разделен на 4 независимых слоя. Связь между слоями осуществляется через **Data Binding** (Контакты) и **Event Bus** (Impulsys), но никогда через прямые ссылки "View -> Logic".

### Слой 1: DRIVERS (Источники воздействия)

* **Роль:** Генерация данных извне (сенсоры, сеть, таймеры, железо).
* **Компоненты:**
  * `Driver`: Интерфейс жизненного цикла (`init`, `update(dt)`, `dispose`).
  * `DriverManager`: Синглтон. Тикает каждый кадр (`ENTER_FRAME`).
  * `MockSensorDriver`: Симулятор данных.
  * `FPSDriver`: Системный мониторинг.
* **Принцип:** Драйверы "впрыскивают" данные напрямую в `Contact`, запуская каскад вычислений, но сами не являются частью логического графа.

### Слой 2: CORE / IO (Ядро логики)

* **Роль:** Чистая математика и трансформация данных. Полная независимость от UI.
* **Ключевые сущности:**
  * **`SignalQueue` (НОВОЕ):** Центральный диспетчер. Реализует паттерн **Trampoline**. Гарантирует плоский стек вызовов при любых глубинах вложенности графа.
  * **`Contact`:** Атомарный носитель данных.
    * *Реактивность:* При изменении значения (`set value`) не вызывает рекурсию, а ставит задачу в очередь (`SignalQueue`).
    * *Связи:* Хранит массив `linkedTargets` и ссылку на `owner` (Atom).
  * **`Atom`:** Функциональный узел.
    * *Zero-Allocation:* Использует кешированный массив `_inputCache` для чтения данных, избегая создания мусора при каждом тике.
    * *Reactive Logic:* Подписан на свои контакты через механизм владельца (`owner`).
  * **`Assembly`:** Композитный контейнер. Управляет жизненным циклом вложенных атомов.
  * **`Blueprint`:** ДНК структуры. Сериализуемое описание графа.
  * **`Impulsys`:** Глобальная шина событий (Observer Pattern) для системных команд.

### Слой 3: EDITOR / ED (Визуализация)

* **Роль:** Инструмент управления графом.
* **Ключевые модули:**
  * **`NodeEditor`:** Менеджер сцены. Поддержка Drag & Drop.
    * *Fix:* Отложенная инициализация (`ADDED_TO_STAGE`) для корректной работы со сценой.
  * **`NodeView`:** Визуал узла.
    * *Реактивность:* Подписывается на `Contact` для отображения значений (зеленые цифры).
    * *Универсальность:* Корректно работает с `Atom` и узлом `SELF` (Assembly).
  * **`WireLayer`:** Рендеринг связей.
    * *Алгоритм:* Кубическая кривая Безье (Cubic Bezier).
    * *Направление:* Касательные векторы всегда направлены "наружу" от портов (Вход -> влево, Выход -> вправо), обеспечивая естественный поток визуализации независимо от порядка соединения.

### Слой 4: DEVICE / GO (Интерфейс пользователя)

* **Роль:** Представление данных конечному пользователю (HMI).
* **Компоненты:**`DevicePanel`, `AtomView`, `SkinManager`.

## 3. Протокол Вычислений (Computation Protocol v2.0)

Переход от **Recursive Push** к **Scheduled Pull/Push**.

1. **Инициатор:** Драйвер или пользовательский ввод меняет `contact.value`.
2. **Планирование:**`Contact` проверяет флаг `_isScheduled`. Если сброшен — добавляет задачу `_propagate` в `SignalQueue`.
3. **Диспетчеризация:**`SignalQueue` выполняет задачи итеративно в цикле `while`.
4. **Каскад:**`_propagate` обновляет связанные контакты. Их `set value` снова планирует задачи. Стек не растет.
5. **Вычисление:** Атом получает уведомление `onContactChanged`, считывает данные в кеш, выполняет логику, записывает результат в выходные контакты.
6. **UI Update:** Подписчики (View) получают уведомления последними.

**Преимущества:**

* Стабильность при цепочках > 1000 узлов.
* Снижение нагрузки на CPU за счет оптимизации "глубины".
* Снижение нагрузки на GC за счет `_inputCache`.

## 4. Визуальные стандарты (Visual Standards)

### Провод (Wire)

* **Стиль:** Natural Flow.
* **Изгиб:** Определяется типом портов.
  * Output Port: `Control Point 1.x = Start.x + Tension` (выход вправо).
  * Input Port: `Control Point 2.x = End.x - Tension` (вход слева).
* **Ghost Wire:** Временный провод при перетаскивании. Имеет повышенную яркость/толщину.

### Узел (Node)

* **Цветовая кодировка:**
  * Input Ports: Оранжевый (`0xFF8800`).
  * Output Ports: Зеленый (`0x00FF88`).
  * Background: Темно-серый (`0x333344`).
  * Values: Зеленый моноширинный текст (`0x00FF00`).

## 5. Библиотека Атомов (Atom Library)

Текущий реестр базовых компонентов:

* **Sources:**
  * `SensorMock`: Генератор случайных чисел.
  * `FPSMonitor`: Вывод FPS.
* **Logic:**
  * `Pass`: Прямая передача (T-pipe).
* **Outputs:**
  * `AlphaNumericLine`: Текстовый дисплей.

## 6. Карта развития (Roadmap)

### Phase 4.1: Persistence (Сохранение)

* Реализация `Serializer` для сохранения/загрузки состояния графа в JSON.
* Интеграция с `LocalStorage` (HTML5) или File System.

### Phase 4.2: Advanced Visuals

* **Orthogonal Routing:** Опциональный режим трассировки "под 90 градусов" (PCB style).
* **Physics Simulation:** Экспериментальный режим "тяжелых проводов" (симуляция гравитации через Verlet Integration).

### Phase 4.3: Core Expansion

* **Typed Contacts:** Введение строгой типизации данных (Number, String, Bool, Impulse).
* **Error Handling:** Механизм передачи ошибок по графу.

---

**Заключение:**Архитектура ALTAURI v4.0 обеспечивает надежную основу для создания сложных визуальных языков программирования, отделяя логику данных от способов их отображения и гарантируя высокую производительность даже при масштабировании.
